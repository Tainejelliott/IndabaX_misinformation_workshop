Retrieval Enhancement
HyDE & Reverse-HyDE
Closing the semantic gap between questions and answers in embedding space
🚧 The Problem — Questions and Answers Live in Different Neighbourhoods
When you embed a question and embed its correct answer, they often land far apart in vector space. Questions use interrogative language; answers use declarative language. A nearest-neighbour search on the raw question may miss the best KB chunk entirely.
❌ Standard RAG fails here
Query: "Is the Great Wall of China visible from space?"

Embed question → search nearest chunks
→ retrieves docs about space / visibility / tourism
→ misses the myth-busting fact paragraph entirely
The query vector lands near interrogative text — not near the declarative answer that says "No, it is not visible — this is a common misconception."
💡 HyDE — Hypothetical Document Embeddings
Instead of embedding the question directly, ask the LLM to generate a plausible answer first — even if some facts may be wrong. Embed that hypothetical answer. Because it uses the same declarative register as real KB chunks, its vector lands much closer to the correct chunk.

Example 1 — "10% of your brain" myth
❓ Real query: "Do humans only use 10% of their brain?"
🤖 HyDE (LLM-generated, may be imperfect):
"This is a widespread myth. Research shows that virtually all brain regions are active and essential. No dormant 90% exists waiting to be unlocked — brain scans show continuous activity across the whole organ."
🎯 Real KB chunk (retrieved):
"Neuroimaging studies demonstrate that all brain regions are metabolically active. The 10% myth likely arose from misquoted research on neural efficiency, not unused capacity."
✓ Both use declarative, factual register → embeddings align
🔄 Reverse-HyDE — Pre-generate a Question for Every Answer
HyDE calls the LLM at query time — adding latency on every search. Reverse-HyDE flips this: at indexing time, for each KB chunk generate synthetic questions it would answer. Store those question embeddings linked to the chunk. At retrieval the real user query is embedded and matched question-to-question — same linguistic register, no LLM call needed during search.

Example 2 — Blood colour myth
📄 KB Chunk:
"Human blood is never blue. Deoxygenated blood is dark red. The blue appearance of veins through skin is caused by how tissue absorbs and reflects different wavelengths of light."
🤖 Synthetic Qs (generated at index time):
"Is blood blue inside the body before it gets oxygenated?"
"Why do veins look blue if blood is always red?"
"What colour is deoxygenated blood?"
❓ Real user query at retrieval time:
"Does blood turn blue when it runs out of oxygen?"
✓ Matches synthetic Q → chunk retrieved, no LLM call needed
💡 HyDE
✅ No indexing overhead
✅ Works on any existing index
⚠️ Extra LLM call per query
⚠️ Higher retrieval latency
🔄 Reverse-HyDE
✅ Fast retrieval — no LLM call
✅ Consistent query latency
⚠️ Upfront indexing cost
⚠️ Must re-index when KB changes
🏆 When to use what
Dynamic KB → HyDE
Static KB → Reverse-HyDE
Both beat naive Q-embedding
Can combine both strategies
